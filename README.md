# F1 Logbook API

A REST API for Formula 1 historical data, built with FastAPI and PostgreSQL.

Users can register, authenticate, and build a personal "logbook" of favourite
drivers, circuits, and races. Alongside that personal side, the API exposes an
F1 encyclopedia: every driver, circuit, constructor, season, and race is served
from a relational model populated from a public data source, including per-season
statistics and championship standings.

## Features

- **Relational data modelling** — 12 tables with foreign keys, uniqueness
  constraints, and database-level cascade rules.
- **Full CRUD** across drivers, circuits, constructors, seasons, races, race
  results, and sprint results.
- **JWT authentication** with bcrypt password hashing, plus role-based
  authorization separating read access from write access.
- **Per-user collections** — many-to-many favourite tables, each row scoped to
  the authenticated user.
- **External API integration** — an admin-triggered, idempotent synchronization
  job that populates the database from Jolpica-F1, with pagination, timeouts, and
  structured error handling.
- **Computed statistics** — season standings, career totals, and circuit lap
  records derived from raw race results rather than stored redundantly.
- **Automatic API documentation** via Swagger UI and ReDoc, generated by FastAPI.

| Config           | `python-dotenv`        | Environment variables kept out of version control                            |
| Server           | Uvicorn                | ASGI server used by the local dev workflow and the deployment                |

## Architecture

```
app/
├── main.py            Application entry point; mounts all routers
├── database.py        Engine, session factory, Base declarative class, DI dependency
├── models.py          SQLAlchemy ORM models (schema definition)
├── schemas.py         Pydantic request/response schemas (API contract)
├── auth.py            Password hashing, token creation, auth dependencies
├── sync.py            Jolpica-F1 client and upsert logic
├── season_history.py  Derived-statistics recomputation
└── routers/
    ├── auth.py
    ├── sync.py
    ├── resources/     Reference data: drivers, circuits, races, results…
    └── favorites/     Per-user collections
```

The design separates three concerns cleanly:

- **Models** define the database schema.
- **Schemas** define the API contract and never leak internal fields.
- **Routers** own the HTTP layer and the transaction boundary.

## Data model

| Entity                                                | Description                                                                            |
|-------------------------------------------------------|----------------------------------------------------------------------------------------|
| `User`                                                | Accounts. Stores a bcrypt hash; `is_admin` gates privileged writes.                    |
| `Driver`                                              | Drivers — name, nationality, photo URL and credit.                                     |
| `Circuit`                                             | Circuits — location, country, length, photo URL and credit.                            |
| `Constructor`                                         | Teams that drivers have raced for.                                                     |
| `Season`                                              | A championship year. `is_completed` distinguishes finished seasons.                    |
| `Race`                                                | One Grand Prix: belongs to a circuit and to a season, identified by `(season, round)`. |
| `RaceResult`                                          | One row per driver per race — grid, finish position, points, status, fastest lap.      |
| `SprintResult`                                        | The same shape as `RaceResult`, for sprint sessions.                                   |
| `DriverSeasonHistory`                                 | Per-driver, per-season derived statistics and championship position.                   |
| `FavoriteDriver` / `FavoriteCircuit` / `FavoriteRace` | Join tables linking a user to reference data.                                          |

Relational integrity is enforced at two levels:

- **Uniqueness constraints** on every natural key — `jolpica_id` per entity,
  `(season, round)` per race, `(race_id, driver_id)` per result.
- **Database-level `ON DELETE`** — `CASCADE` for dependent results and
  favourites, `SET NULL` for the optional `constructor_id`, so deleting a team
  preserves the historical result rows.

## Derived data

`DriverSeasonHistory` is **never written directly**. It is rebuilt from
`RaceResult` and `SprintResult` by `recalculate_season_history(season, db)`
(`app/season_history.py`).

Every route that can affect those source rows calls that function before
committing, so statistics cannot drift out of sync with the underlying results.
Drivers are ordered by points, then by counts of each finishing position from
first downwards, with driver ID as a final deterministic tie-breaker.

Championship standings are exposed at
`GET /seasons/{season}/standings`, and career totals at
`GET /drivers/{driver_id}/stats`.

## Data source and synchronization

F1 data comes from [Jolpica-F1](https://api.jolpi.ca/ergast/f1) (an
Ergast-compatible API), which provides historical data from 1950 onward and
requires no authentication.

The application **never calls Jolpica on a user request**. An administrator
triggers a synchronization per season:

```http
POST /sync/2024
Authorization: Bearer <admin token>
```

The job is idempotent — it upserts by `jolpica_id`, reporting created versus
updated counts for every entity. Design points worth noting:

- All HTTP calls complete **before** any database writing begins, so a failing
  upstream request cannot leave a half-written season.
- Results are paginated at 100 records per page, and the loop is bounded by the
  total count reported in the payload.
- A missing or malformed field raises a domain-specific `JolpicaSyncError`,
  surfaced to the caller as **502 Bad Gateway** rather than a generic 500, keeping
  upstream failures distinguishable from internal errors.
- Requests carry an explicit `User-Agent` and a 20-second timeout.

The API always reads and writes against its own database, so it stays available
independently of the upstream service.

Driver and circuit photographs are curated by hand from
[Wikimedia Commons](https://commons.wikimedia.org) under Creative Commons
licenses, stored separately from the automated sync.

## Authentication and authorization

- `POST /auth/register` creates an account and returns the new user.
- `POST /auth/login` returns a short-lived bearer token.
- `GET /auth/me` returns the authenticated user.
- `PATCH /auth/users/{user_id}/admin` grants or revokes administrator rights on
  another account. An administrator cannot revoke their own.

Two dependencies enforce access control:

| Dependency         | Grants                                                                       |
|--------------------|------------------------------------------------------------------------------|
| `get_current_user` | Any authenticated user. Owns their own favourites.                           |
| `require_admin`    | Writes to reference data, user promotion, and the sync endpoint.             |

Reads on reference data are intentionally **public** — the encyclopedia is
readable without an account — while every mutation that would alter shared F1
data requires admin rights. Passwords are stored as bcrypt hashes; the 72-byte
maximum on `password` respects bcrypt's input limit.

| **Drivers**        | `POST` `GET /`, `GET` `PATCH` `DELETE /{driver_id}`                                            |

## Getting started

### Requirements

- Python 3.11+
- A reachable PostgreSQL instance

### Installation

```bash
git clone https://github.com/Fernandotb96/f1-logbook.git
cd f1-logbook

python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

### Configuration

Create a `.env` file in the project root. It is gitignored and must never be
committed.

```bash
DATABASE_URL=postgresql+psycopg2://user:password@localhost:5432/f1_data
SECRET_KEY=<a-long-random-string>
ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=30
```

| Variable                      | Required | Purpose                                                                   |
|-------------------------------|----------|---------------------------------------------------------------------------|
| `DATABASE_URL`                | Yes      | PostgreSQL connection string. Use the explicit `+psycopg2` driver suffix. |
| `SECRET_KEY`                  | Yes      | Signs JWTs. Generate with `openssl rand -hex 32`.                         |
| `ALGORITHM`                   | No       | JWT signing algorithm. Defaults to `HS256`.                               |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | No       | Token lifetime. Defaults to `30`.                                         |

The application refuses to start if `DATABASE_URL` or `SECRET_KEY` is missing.

### Running

```bash
uvicorn app.main:app --reload
```

- Swagger UI — <http://127.0.0.1:8000/docs>
- ReDoc — <http://127.0.0.1:8000/redoc>

### Populating data

1. Register a user.
2. Promote it to admin. There is no self-service path for the *first*
   administrator, so this one step takes a direct database write:
   ```sql
   UPDATE users SET is_admin = true WHERE email = 'you@example.com';
   ```
   Every administrator after that can be promoted over the API with
   `PATCH /auth/users/{user_id}/admin`.
3. Request a token and trigger a sync:
   ```bash
   curl -X POST http://127.0.0.1:8000/sync/2024 -H "Authorization: Bearer <token>"
   ```

Tables are created automatically at startup.

## Deployment (Render)

The API runs on Render as a **Web Service** backed by a **PostgreSQL**
instance, both created from the dashboard.

### 1. Create the database

**New → PostgreSQL**, Free plan. Note the *External Database URL*, which looks
like `postgres://USER:PASSWORD@HOST/DBNAME`.

### 2. Create the web service

**New → Web Service**, pointed at this repository.

| Setting        | Value                                              |
|----------------|----------------------------------------------------|
| Language       | Python 3                                           |
| Build command  | `pip install -r requirements.txt`                  |
| Start command  | `uvicorn app.main:app --host 0.0.0.0 --port $PORT` |

`--host 0.0.0.0` and `--port $PORT` are not optional: Render cannot reach the
container on `127.0.0.1`, and the port it assigns is only known at runtime.

### 3. Set the environment variables

Settings → Environment:

| Variable                     | Value                                                             |
|------------------------------|-------------------------------------------------------------------|
| `DATABASE_URL`               | The external database URL with its scheme rewritten — see step 4  |
| `SECRET_KEY`                 | A long random string. Generate a fresh one for production; never reuse a local key |
| `ALGORITHM`                  | `HS256`                                                           |
| `ACCESS_TOKEN_EXPIRE_MINUTES`| `30`                                                              |
| `PYTHON_VERSION`             | `3.14`. Optional: `.python-version`|

### 4. Rewrite the database URL

Render hands out `postgres://…`, but SQLAlchemy needs the driver to be
explicit. Change the scheme, and nothing else:

```
postgres://USER:PASSWORD@HOST/DBNAME
postgresql+psycopg2://USER:PASSWORD@HOST/DBNAME
```

Everything after the scheme stays byte-for-byte identical — including the
absence of a port number, which defaults to 5432.

### 5. Deploy

Push to `main`. Render installs the pinned dependencies, `app/main.py` creates
the tables at import time, and the interactive documentation appears at
`https://HERE_YOUR_SERVICE.onrender.com/docs`.

Promote the first administrator once the database exists, as described in
[Populating data](#populating-data).

### Free tier caveats

- **The free database expires 30 days after it is created**, whether or not it
  has been used. You then get a **14-day grace period** to upgrade to a paid
  plan; when that ends Render deletes the database and all of its data. Create
  another free database when you need one — the schema is rebuilt
  automatically at startup, but the rows are gone, so export anything worth
  keeping beforehand.
- **The web service spins down after 15 minutes without traffic.** The first
  request afterwards takes about a minute to answer. `pool_pre_ping=True` is
  already set in `app/database.py`, so a connection that died while the service
  slept is discarded and replaced instead of failing the request.
- The workspace gets **750 free instance hours per calendar month**, shared
  across every free service and reset on the 1st.
- Free compute is **0.1 CPU / 512 MB RAM** and free storage is **1 GB**.
- There is **no autoscaling and no cron**: this service is a single process,
  which is enough for a read-mostly API with an admin-triggered sync.

## Design decisions

**Schema derived, never duplicated.** Rather than storing career totals and
championship positions, those are recomputed from raw results on every
mutation. This trades a small amount of write-time work for the guarantee that
statistics can never disagree with the results they summarize.

**Transaction ownership.** Routers own the transaction boundary and commit or
roll back; `sync.py` and `season_history.py` mutate and flush but never commit.
This keeps the sync layer reusable and prevents partial-commit bugs.

**Separate race and sprint results.** The two tables share a shape but differ in
meaning, so keeping them distinct keeps sprint sessions queryable independently
of race classification and allows the two result sets to evolve separately.

**`bcrypt` used directly.** Wrapping it in `passlib` would add a dependency
layer for no functional gain, and `passlib`'s current releases have known
compatibility issues with modern `bcrypt` releases.

**Explicit driver in the database URL.** Using `postgresql+psycopg2://` rather
than `postgresql://` makes the driver unambiguous and independent of which
psycopg packages happen to be installed.

## Current limitations

Known and documented rather than hidden:

- **No migrations.** Tables are created with `Base.metadata.create_all()` at
  startup, which creates missing tables but does not alter existing ones.
  Introducing Alembic is the next step.
- **No automated tests.** The sync layer is written with an injectable HTTP
  client specifically to make this practical.
- **No pagination** on list endpoints; they return full table scans.
- **No admin bootstrap.** The first administrator must be promoted manually;
  every administrator after that can be granted through the API.
- **No user management.** The application does not support password reset or
  account deletion.
- **No frontend.** The API is only accessible from the command line.
